# Growel Promotional Operations Dashboard

The app is built with React and JavaScript. Real accounts and operational records are stored in Microsoft SQL Server. The app server requires Node.js 22.9 or later and must run as a Node.js server; static-only hosting is not supported.

## Project structure

This is a single full-stack TanStack Start application, not separate frontend and backend deployments. The React pages, HTTP API routes, and Node.js server are built and deployed together.

```text
src/
  routes/                     React pages and server API endpoints
    _authenticated/           Signed-in operational pages
    api/                       Login, user, permission, and operations APIs
  components/                  Shared React components
  lib/                         Shared app utilities and browser-side API client
  server/                      SQL access, authentication, and operations logic
  router.jsx                   TanStack Router configuration
  start.js                     TanStack Start request middleware
  server.js                    Node server entry and SSR error handling
  styles.css                   Global app styles
database/
  schema.sql                   New-database SQL schema
  migrations/                  Existing-database schema updates
public/                         Static assets served by the app
scripts/                        Admin bootstrap utility
.output/                        Generated production build (do not edit or commit)
```

The browser-facing frontend lives in `src/routes/_authenticated/`, `src/routes/auth.jsx`, `src/components/`, and `src/styles.css`. HTTP API endpoints live in `src/routes/api/`; they call backend logic in `src/server/`. The `src/server/` directory is part of the same application, not a separately deployed service. `src/routeTree.gen.js` is generated by TanStack Router and should not be edited manually.

For production, build the full application with `npm run build` and run the generated Node.js server with `npm run start`. Deploy the project root and its package manifest/lockfile; do not deploy only `public/` or `src/routes/`.

## Set up SQL Server

1. Create a new, empty SQL Server or Azure SQL database for this app.
2. Connect to that database in SQL Server Management Studio or Azure Data Studio and run [`database/schema.sql`](./database/schema.sql). This creates the tables and the default roles and permissions.
3. Configure the app's SQL login with data-reader and data-writer access to the database, plus permission to use the request-number sequence. For Azure SQL, a database administrator can grant the runtime user these permissions:

   ```sql
   ALTER ROLE db_datareader ADD MEMBER [growel_app];
   ALTER ROLE db_datawriter ADD MEMBER [growel_app];
   GRANT UPDATE ON OBJECT::dbo.request_number_sequence TO [growel_app];
   ```

   Replace `growel_app` with the database user name. Use a separate administrator login to create the database and run the schema; do not run the app with a database-owner account.

## Configure and run

1. Copy `.env.example` to `.env` and set `SQL_SERVER`, `SQL_DATABASE`, `SQL_USER`, and `SQL_PASSWORD` to the server-only SQL connection details. Keep `SQL_ENCRYPT=true` and `SQL_TRUST_SERVER_CERTIFICATE=false` for production.
2. Set `SESSION_SECRET` to a random secret of at least 32 characters. To generate one with Node.js:

   ```sh
   node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
   ```

3. Set `BOOTSTRAP_ADMIN_EMAIL`, `BOOTSTRAP_ADMIN_NAME`, and `BOOTSTRAP_ADMIN_PASSWORD` to the initial Admin account details. The password must be 12–200 characters.
4. Install and bootstrap the first Admin:

   ```sh
   npm install
   npm run bootstrap:admin
   ```

   Run this command only once. After success, remove the three `BOOTSTRAP_ADMIN_*` values from `.env` and retain the SQL connection settings and `SESSION_SECRET`.
5. Start locally with `npm run dev`. Open `/api/health` to verify that the app server can connect to SQL Server; a successful response reports `"database":"connected"`.

The sign-in page uses SQL-backed email and password accounts. An Admin creates an employee profile and login together from the Employees page; the same employee directory includes initial Admin accounts and approved sign-ups. Admins can separately set each employee's login access to Enabled or Disabled and work status to Active or Inactive, then save the changes. Disabling login prevents sign-in without changing the employee's work status. Admins manage roles and permissions in the Permission control panel. Passwords are stored as salted scrypt hashes, and the session is held in an HttpOnly cookie.

## Sign-up and account administration

Self-sign-up accepts only `@growelfeeds.com` email addresses. New users provide their name, requested role, region, and approving authority; these remain pending until an Admin confirms the role and profile from the Employees page. Approval creates the employee profile and login together. Executive requests then use the name, role, region, and approving authority from the signed-in user and employee profile, rather than trusting editable request-form values. The Admin can reject pending requests and reset active employees' passwords there as well. Password resets and employee/login creation are restricted to Admins; passwords are never displayed or stored in plain text.

For an existing database, apply [`database/migrations/20261102_add_signup_requests.sql`](./database/migrations/20261102_add_signup_requests.sql), [`database/migrations/20261102_add_request_profile_fields.sql`](./database/migrations/20261102_add_request_profile_fields.sql), and [`database/migrations/20261103_add_material_language.sql`](./database/migrations/20261103_add_material_language.sql) before deploying this version. New databases receive the same tables and profile fields from [`database/schema.sql`](./database/schema.sql).

## Reports

The Reports page filters the available records by request year and exports that filtered view to `.xlsx` and PDF. Demo sessions report browser-local sample records; signed-in production sessions report the request records available to that user. Request values are visible only to Admin and HR; other roles receive count-based reports without request-value data.

## Production deployment

Deploy the built app to a Node.js 22.9+ host that supports a persistent Node server process. Configure SQL credentials and `SESSION_SECRET` as the host's private environment secrets, allow the host to reach the SQL Server firewall/network, then run:

```sh
npm run build
npm run start
```

Do not commit `.env` or put database credentials in browser-exposed `VITE_*` variables. Keep the database firewall restricted to trusted app and administration networks.

### Deploy to Render

The included [`render.yaml`](./render.yaml) configures a Node web service, production build/start commands, and the `/api/health` check. To deploy:

1. Push this repository to GitHub without `.env`, the project ZIP, or the request PDF. The ZIP and PDF are excluded by `.gitignore`.
2. In Render, create a Blueprint instance and connect the GitHub repository. Review the `growel-promotional-dashboard` web service on the Free plan. Free services can sleep when idle and may take longer to respond on the first request.
3. Enter `SQL_SERVER`, `SQL_DATABASE`, `SQL_USER`, `SQL_PASSWORD`, and a unique `SESSION_SECRET` when Render prompts for the private values. Do not put these in the repository. Keep the SQL encryption settings enabled.
4. Configure the SQL Server firewall to allow the Render service to connect. Deploy and wait for `/api/health` to pass.
5. Before opening the service to users, run `npm run bootstrap:admin` once from a trusted machine with `.env` configured to the production database, then remove the `BOOTSTRAP_ADMIN_*` variables from that local `.env`. Never add bootstrap passwords to the repository or Render logs.

Render deploys subsequent commits automatically. The application stores live operational data in SQL Server; this service does not deploy a static-only site or create the database schema automatically.

## Local demo mode

When running `npm run dev`, the sign-in page provides browser-only demo identities for Executive, RM, AVP, GM, HR, and Admin. Demo records and permission settings are local test data; they are not SQL accounts and do not access the database. Demo sign-in options are disabled in production builds.
